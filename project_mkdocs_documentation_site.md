Built a self-hosted documentation site for the whole home-lab setup (this was the "wiki/documentation server" idea flagged as next-up in [[project_p1monitor_influxdb_pipeline]] — "de configuratie is behoorlijk complex aan het worden").

**Repo:** private GitHub repo `git@github.com:WilcoKakkenberg/MkDocs.git`, standard mkdocs layout (`mkdocs.yaml` at root, `docs/` subfolder with `index.md`, `architectuur.md`, `homeassistant.md`). `repo_url`/`edit_uri: edit/main/docs/` set in `mkdocs.yaml` for GitHub's edit-pencil links. Mermaid diagrams work out of the box via the `pymdownx.superfences` custom fence already in the config - no `extra_javascript` needed. Root page requires a file literally named `index.md` (MkDocs won't build `/` otherwise) - `home.md` was renamed via `git mv`.

**Final production architecture on the QNAP (in `qnap-containers.yaml`, working as of 2026-08-28):** two services replacing the old single `mkdocs serve`-dev-server container:
- `mkdocs-sync`: stock `squidfunk/mkdocs-material:latest` image (git+openssh-client already built in, verified - no custom build needed), `user: "1001:100"`, entrypoint overridden to a bind-mounted script (`/share/Container Data/mkdocs/scripts/sync-and-build.sh`, NOT baked into an image - deliberate, so it's editable without a rebuild). Loops forever: `git pull --ff-only` + `mkdocs build -f mkdocs.yaml -d /site` every `SYNC_INTERVAL_SECONDS` (300s). Auth via an **SSH deploy key** (read-only, added under the GitHub repo's Settings → Deploy keys) instead of a PAT, specifically because the container is ephemeral and a PAT would need periodic re-entry - deploy keys don't expire. Key lives in a bind-mounted `/ssh` dir (not `$HOME/.ssh`), referenced via explicit `GIT_SSH_COMMAND="ssh -i $SSH_DIR/id_ed25519 -o UserKnownHostsFile=$SSH_DIR/known_hosts"`.
- `mkdocs-web`: `nginx:alpine` serving the built `/site` dir read-only, keeps the old static IP `172.10.1.27` and port `8005`.

**Deployment gotchas hit and fixed, in order (worth knowing before touching this again):**
1. `docker compose ... --build` failed with `mkdir .../container-station/homes/qnap-admin: permission denied` - Container Station's per-user build-cache home dir is owned by `admin` only (`drwxr-x---`), `qnap-admin` (a non-admin SSH user) can't write there. **Avoided entirely** by not building a custom image at all (see above) rather than using `sudo` - user explicitly did not want to run the compose file as root.
2. Files copied/edited from Windows got **CRLF line endings**, causing `exec /sync-and-build.sh: exec format error`. `sed -i 's/\r$//'` alone wasn't fully trusted (no `xxd`/`od` on this QNAP shell to verify) - the reliable fix was writing the file directly on the QNAP via an SSH heredoc (`cat > file <<'EOF' ... EOF`), which guarantees clean LF with no BOM.
3. `ssh-keygen` and (persistently) `ssh` itself both fail with `No user exists for uid 1001` - OpenSSH hard-requires a `/etc/passwd` entry for the current uid (unlike `git`, which works fine without one). Fixed by bind-mounting a custom `/etc/passwd` over the image's own (copy of the original + one added line for uid 1001) - not by running as root. One-off `ssh-keygen` itself still needed a scoped `docker exec -u 0` (root only for that single exec, not the persistent process).
4. Generated private key had mode `0640` (group-readable) from the `-u 0`-generated + `chown`-ed file - SSH refuses group/other-readable private keys ("bad permissions"). Fixed with `chmod 600`.
5. **The QNAP's `/share/Container Data` (or at least the `mkdocs` folder within it) enforces its own permission/ownership behavior independent of what a container's process requests.** Newly created files/dirs always come out `rwxrwx---` / `rw-rw----` (group rwx, zero "other" access) no matter what `umask` the writing process sets - confirmed via `getfacl`: there's a real POSIX default ACL on the folder (`default:mask::rwx` etc.) that overrides umask on inheritance. This is why `mkdocs-web` (nginx, uid 101/gid 101 by default) got 403 reading files owned by `1001:100` - it wasn't in the owning group.
6. Tried `group_add: ["100"]` on the nginx service (Docker-level supplementary group) - **did not work**, because nginx's own worker processes call `setgid()`/drop-privileges internally based on its `user` directive in `nginx.conf`, which resets supplementary groups independent of what Docker assigned to the container.
7. Tried overriding nginx.conf's `user` directive to `user nginx 100;` (numeric gid) - failed: `getgrnam("100") failed` - nginx's `user` directive's group argument is always resolved by **name** (`getgrnam`), never treated as a raw numeric GID even if the string looks numeric. Fixed by using the group's real name instead (gid 100 is named `users` on this image) - but that alone still 403'd.
8. Confirmed via `/proc/<worker-pid>/status` that the worker really did run with `Gid: 100 100 100 100` after the `user nginx users;` fix, and via `getfacl` that the ACL math should allow that gid read access - yet a **raw isolated test** (`docker run --user 101:100 ... cat file` on the same bind mount, no nginx involved at all) *also* got `Permission denied`. This proved it isn't an nginx quirk (ruled out `sendfile` too, which is a separate known NAS+nginx 403 cause but wasn't the issue here) - it's this QNAP's ACL/identity enforcement rejecting **any uid/gid that isn't a real recognized QNAP user account**, regardless of what plain POSIX permission bits or `getfacl` output say should be allowed. uid `1001` happens to coincide with the real QNAP account `qnap-admin`, which is why the `mkdocs-sync` container (already running as `1001:100`) never had this problem, while nginx's default `101:101` (a "foreign", QNAP-unrecognized identity) got silently rejected beneath the POSIX layer.
9. **Final fix:** rather than chasing group-based access further, gave `mkdocs-web` its own bind-mounted `/etc/passwd` too (same technique as step 3), adding a `mkdocs:x:1001:100:...` entry, and set `nginx.conf`'s `user mkdocs users;` - so nginx's workers run *as uid 1001 itself* (the recognized QNAP identity), not merely a matching gid. That resolved it: `curl -I http://localhost:8005` → `200 OK`.

**How to apply:** if `mkdocs-web` or `mkdocs-sync` ever needs recreating and 403s or "No user exists" errors reappear, the fix is already known (steps above) - don't re-derive from scratch. If the `data`/`site`/`ssh` directories under `/share/Container Data/mkdocs/` ever show up owned by `admin:administrators` and empty again (happened once, cause unconfirmed - possibly Docker auto-creating a missing bind-mount source), just re-`chown -R 1001:100` and let `mkdocs-sync` re-clone from GitHub - no data is lost since GitHub is the source of truth.
